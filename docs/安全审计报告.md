## 二、严重风险

### S-1. 默认管理员密码 `admin123` 硬编码

- **文件**: `common/db/init_database.py:3324`
- **代码**:
  ```python
  password_hash = get_password_hash("admin123")
  ```
- **上下文**: `create_default_admin()` 方法在数据库初始化时创建用户名 `admin`、密码 `admin123` 的管理员账户（第3308-3338行）。
- **风险分析**: 部署后如果不修改默认密码，攻击者可直接用 `admin/admin123` 登录系统获取管理员权限。虽然 `backend-web/app/api/routes/auth.py:191` 提供了 `check-default-password` 接口（需管理员调用），但**不强制**修改密码，首次部署后系统处于弱密码暴露状态。
- **利用条件**: 目标系统未修改默认密码 + backend-web 端口可达（默认8089）。
- **修复建议**: 首次登录强制修改密码；或在部署脚本中要求设置管理员密码。

### S-2. docker-compose.yml / deploy.sh 默认数据库密码

- **文件**: `docker-compose.yml:14,17` / `deploy.sh:~.env模板` / `deploy_remote.sh:~.env模板` / `update.sh:~.env模板`
- **代码**:
  ```yaml
  MYSQL_ROOT_PASSWORD=${MYSQL_ROOT_PASSWORD:-xianyu@2026}
  MYSQL_PASSWORD=${MYSQL_PASSWORD:-xianyu@2026}
  REDIS_PASSWORD=${REDIS_PASSWORD:-xianyu@2026}
  ```
- **风险分析**: 所有部署脚本（`deploy.sh`、`deploy_remote.sh`、`update.sh`）生成的 `.env` 文件均硬编码默认密码 `xianyu@2026`。如果用户不手动修改 `.env`，MySQL root 密码、普通用户密码和 Redis 密码全部使用同一默认值。`deploy_remote.sh` 场景下 MySQL/Redis 暴露在远程主机，默认密码可被远程利用。
- **利用条件**: 目标使用默认部署配置 + 数据库端口对外可达。
- **修复建议**: 部署脚本生成 `.env` 时使用随机密码，或拒绝使用默认密码启动。

### S-3. `EXTERNAL_API_KEY` 默认值 `zhinian_bk`

- **文件**: `docker-compose.yml:92` / `deploy.sh:.env模板` / `deploy_remote.sh:.env模板` / `update.sh:.env模板`
- **代码**:
  ```yaml
  EXTERNAL_API_KEY=${EXTERNAL_API_KEY:-zhinian_bk}
  ```
- **风险分析**: `EXTERNAL_API_KEY` 用于"对接卡密秘钥"一键创建的鉴权（基址 `CARD_DOCK_BASE_URL`）。默认值 `zhinian_bk` 是公开可见的弱密钥，攻击者可利用该密钥调用上游卡券服务接口。
- **利用条件**: 目标未修改默认 `EXTERNAL_API_KEY` + `CARD_DOCK_BASE_URL` 可达。
- **修复建议**: 部署时强制生成随机密钥，禁止使用默认值。

## 三、高风险

### H-1. websocket `/internal/*` 路由完全无认证

- **文件**: `websocket/app/api/routes/internal.py` 全文（39行定义 `router = APIRouter(prefix="/internal")`）
- **涉及接口**:
  - `POST /internal/accounts/{account_id}/start` — 启动任意账号任务
  - `POST /internal/accounts/{account_id}/stop` — 停止任意账号任务
  - `POST /internal/accounts/{account_id}/restart` — 重启任意账号任务
  - `POST /internal/captcha/solve` — 远程触发滑块验证（可操作 Cookie 写回）
  - `POST /internal/accounts/{account_id}/send-message` — 以任意账号身份发送消息
  - `POST /internal/orders/deliver` — 触发订单发货
  - `POST /internal/orders/confirm-no-logistics` — 确认无物流发货
  - `POST /internal/orders/cancel` — 取消订单
  - `POST /internal/logs/retention` — 修改日志保留天数
  - `GET /internal/accounts/connection-stats` — 查询连接状态
  - `GET /internal/accounts/{account_id}/status` — 查询账号状态
- **风险分析**: 所有 `/internal` 路由无任何认证（无 JWT、无 API Key、无 IP 白名单）。设计意图是供 backend-web 通过 Docker 内网调用，但 websocket 端口（默认8090）在 `docker-compose.yml:162` 映射到宿主机。如果宿主机端口对公网开放，攻击者可直接调用这些接口操控任意账号：发送消息、触发发货、停止/启动账号、注入 Cookie。
- **利用条件**: websocket 端口（8090）对攻击者可达。
- **修复建议**: 为 `/internal` 路由添加共享密钥校验或 IP 白名单；或不在 docker-compose 中映射 websocket 端口到宿主机。

### H-2. scheduler `/internal/*` 路由完全无认证

- **文件**: `scheduler/app/api/routes/internal.py` 全文（21行定义 `router = APIRouter(prefix="/internal")`）
- **涉及接口**:
  - `POST /internal/logs/retention` — 修改日志保留天数
  - `POST /internal/tasks/reload` — 重新加载任务配置
  - `GET /internal/tasks/status` — 查询任务状态
  - `POST /internal/tasks/{task_code}/trigger` — 手动触发任意定时任务
  - `POST /internal/account-cooldown/clear` — 解除账号风控冷却
  - `POST /internal/tasks/listing_monitor/run/{task_id}` — 执行商品监控
  - `POST /internal/system/self-restart` — 重启 scheduler 服务
- **风险分析**: 与 websocket 同理，scheduler 端口（默认8091）在 `docker-compose.yml:213` 映射到宿主机。攻击者可远程触发定时任务、解除风控、重启服务。
- **利用条件**: scheduler 端口（8091）对攻击者可达。
- **修复建议**: 同 H-1。

### H-3. `launcher/config_store.py` 使用 base64 存储 MySQL/Redis 密码

- **文件**: `launcher/config_store.py:54`
- **代码**:
  ```python
  # base64 编解码存储密码到 data/connection.dat
  ```
- **风险分析**: 桌面客户端将数据库连接密码用 base64 编码后存入 `data/connection.dat`。注释自述"防止明文泄露"，但 base64 是编码而非加密，任何人可直接解码获取明文密码。如果 `connection.dat` 被窃取（如通过文件下载漏洞或物理访问），数据库密码即刻暴露。
- **利用条件**: 攻击者获取 `data/connection.dat` 文件。
- **修复建议**: 使用操作系统提供的密钥管理服务（Windows DPAPI / macOS Keychain）加密存储。

### H-4. `launcher/activation.py` 硬编码激活码签名盐值

- **文件**: `backend-web/app/api/routes/activation.py:32`（注：摘要中记录为 `launcher/activation.py`，实际路径为 `backend-web/app/api/routes/activation.py`）
- **代码**:
  ```python
  _SECRET_SALT = "XianyuAutoReply@2024#Lic"
  ```
- **风险分析**: 激活码使用 SHA256 + 硬编码盐值签名。盐值固定在源码中，任何能获取源码的人都能伪造有效激活码，绕过授权机制。
- **利用条件**: 攻击者获取源码 + 理解激活码生成算法。
- **修复建议**: 将盐值移至服务端动态生成或使用非对称签名（如 HMAC with server-managed key）。

## 四、中风险

### M-1. CORS 配置为 `*`（允许所有来源）

- **文件**: `docker-compose.yml:85` / `deploy.sh` / `deploy_remote.sh` / `update.sh` 生成的 compose 文件
- **代码**:
  ```yaml
  CORS_ORIGINS=*
  ```
- **风险分析**: 所有部署配置中 CORS 设置为 `*`，允许任意网站的 JavaScript 代码跨域访问 API。结合 JWT 认证（存储在 localStorage），恶意网站可发起跨域请求利用用户已登录的会话。
- **修复建议**: 生产环境将 `CORS_ORIGINS` 限制为前端实际域名。

### M-2. `common/utils/service_restart.py` 内联脚本通过 `subprocess.Popen` 执行

- **文件**: `common/utils/service_restart.py:279-290, 375-467`
- **代码**:
  ```python
  subprocess.Popen(
      [reviver_python, "-c", reviver_code],
      ...
  )
  ```
- **风险分析**: `_REVIVER_TEMPLATE`（375-467行）是一段内联 Python 脚本，通过 `subprocess.Popen` 以 `-c` 参数执行。脚本从环境变量读取端口、延迟、工作目录和启动命令。虽然参数来自 `SERVICE_META` 硬编码配置（非用户可控），但如果攻击者能注入环境变量（如通过 docker-compose 篡改），可能影响重启行为。实际风险评估为**中低**，因为参数来源受控。
- **修复建议**: 将内联脚本提取为独立 `.py` 文件，避免 `-c` 执行动态代码。

### M-3. `admin.py` 日志导出路径穿越残留风险

- **文件**: `backend-web/app/api/routes/admin.py:474`
- **代码**:
  ```python
  safe_name = Path(file).name
  if not safe_name.endswith(".log"):
      raise HTTPException(status_code=400, detail="只能导出.log文件")
  log_path = log_dir / safe_name
  ```
- **风险分析**: 使用 `Path(file).name` 提取文件名防止目录穿越（如 `../../etc/passwd` 会被截为 `passwd`），且限制 `.log` 后缀。但 `Path.name` 不防御符号链接：如果 `log_dir` 下存在名为 `evil.log` 的符号链接指向系统文件，管理员可读取该文件内容。需管理员权限才可利用，风险降低。
- **修复建议**: 使用 `log_path.resolve()` 检查解析后路径是否仍在 `log_dir` 范围内。

### M-4. `scheduler/app/services/scheduler/cleanup_browser_data_task.py` 目录删除

- **文件**: `scheduler/app/services/scheduler/cleanup_browser_data_task.py:139,151`
- **代码**:
  ```python
  user_data_dir = self.browser_data_dir / f"user_{account_id}"
  shutil.rmtree(user_data_dir, ignore_errors=False)
  ```
- **风险分析**: `account_id` 来自数据库，用于拼接目录路径 `user_{account_id}`。如果 `account_id` 包含路径穿越字符（如 `../../`），理论上可删除 `browser_data_dir` 之外的目录。但 `account_id` 在写入数据库时通常已有格式约束，且定时任务由系统自动触发而非用户直接控制，实际利用难度较高。
- **修复建议**: 对 `account_id` 做路径字符过滤（如 `re.sub(r'[^A-Za-z0-9_-]', '', account_id)`）。

### M-5. websocket `/internal/captcha/solve` 可注入 Cookie 并写回数据库

- **文件**: `websocket/app/api/routes/internal.py:362-878`
- **代码**:
  ```python
  @router.post("/captcha/solve")
  async def solve_captcha(request: SolveCaptchaRequest):
      # ... 接收 cookies、account_row_id，成功后写回数据库
      await merge_account_cookie_fields(int(request.account_row_id), raw_id, cookie_updates)
  ```
- **风险分析**: 此接口接收外部传入的 Cookie 和账号行 ID，成功后直接写回数据库。结合 H-1（无认证），攻击者可通过此接口向任意账号注入恶意 Cookie，可能导致账号劫持。虽然 `account_id` 做了正则清洗（第381行 `re.sub(r"[^A-Za-z0-9_-]", "", raw_id)`），但 `account_row_id` 是整数类型，无归属校验。
- **修复建议**: 添加认证 + 校验 `account_row_id` 归属。

## 五、低风险

### L-1. `launcher/gui*.py` gzip 解压远程数据

- **文件**: `launcher/gui.py:111` / `launcher/gui_about.py:152` / `launcher/gui_dashboard.py:129,286`
- **代码**:
  ```python
  raw = gzip.decompress(raw)
  ```
- **风险分析**: GUI 从 `https://xy.zhinanboke.com` 下载图片/数据并 gzip 解压。数据来源是固定的官方服务器，非用户可控。理论上如果官方服务器被入侵，可返回恶意压缩数据触发 gzip 炸弹（解压耗尽内存），但实际风险低。
- **修复建议**: 限制解压后数据大小。

### L-2. `deploy.sh` / `deploy_remote.sh` / `update.sh` 中硬编码默认密码模板

- **文件**: `deploy.sh`（.env ENVEOF 模板）/ `deploy_remote.sh`（.env.remote ENVEOF 模板）/ `update.sh`（.env ENVEOF 模板）
- **代码**: 所有 `.env` 模板中均硬编码 `MYSQL_PASSWORD=xianyu@2026`、`REDIS_PASSWORD=xianyu@2026`、`EXTERNAL_API_KEY=zhinian_bk`。
- **风险分析**: 与 S-2/S-3 相关。这些是模板默认值，用户需手动修改。`deploy_remote.sh` 还硬编码了 `MYSQL_PASSWORD=xianyu@2026` 作为远程数据库连接密码默认值。
- **修复建议**: 部署脚本生成随机密码并写入 `.env`。

### L-3. `launcher/service_runner.py` marshal.loads 加载 .pyc 文件

- **文件**: `launcher/service_runner.py:76,81`
- **代码**:
  ```python
  code_obj = marshal.loads(code_data)
  exec(code_obj, module.__dict__)
  ```
- **风险分析**: 自定义 `PycFileFinder` 从 `.pyc` 文件加载模块。这是 Python 标准的 .pyc 加载机制，非远程代码执行。但如果 `.pyc` 文件被替换为恶意版本（供应链攻击），`marshal.loads` + `exec` 会执行任意代码。该路径仅用于本地 frozen 模式启动，风险低。
- **修复建议**: 对 .pyc 文件做完整性校验（如 HMAC 签名）。

## 六、信息项

### I-1. JWT 密钥数据库回退默认值 `change-me`

- **文件**: `backend-web/app/core/config.py` / `common/core/config.py:66`
- **代码**:
  ```python
  jwt_secret_key: str = Field(default="change-me")
  ```
- **风险分析**: 配置默认值为 `change-me`，但运行时由 `backend-web/app/services/jwt_secret_service.py:62` 的 `ensure_jwt_secret_key()` 从数据库加载或生成强随机密钥覆盖。`common/utils/security.py` 中的 `WEAK_JWT_SECRETS` 黑名单包含 `change-me`，启动时会检测并替换。仅在数据库不可用时回退使用默认值，且此时会记录告警日志。
- **结论**: 设计合理，风险可接受。

### I-2. `backend-web/app/api/routes/external_cookie.py` 无登录态接口

- **文件**: `backend-web/app/api/routes/external_cookie.py:87`
- **代码**:

- **结论**: 安全设计合理，风险可接受。
